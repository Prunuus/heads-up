### Loading and re-bucketing

- `load_deals("train_data")`: 0.05-0.07 s from a warm page cache.
  - Buckets and showdown take 34 MB of arrays (17 bytes a deal); peak RSS is 67 MB, of which 33 MB is the interpreter and imports.
  - With `cards=True`: 0.09 s, 96 MB. With `features=True` as well: 0.19 s, 291 MB.
- `--rebucket` of the 2M against a 400/200/200/200 refit (same designs, seed 0) took 2.2 s. Going back to `data/buckets.npz` took 5.0 s.
  - Both are bound by disk writes; the CPU work is 0.8 s per million deals.
  - The round trip gave back bit-identical buckets.
  - 500 random deals matched the refit's `bucket()` on their cards with 0 mismatches.
  - While the dataset was on the refit, `load_deals` refused the default table.
- Why the features are stored as float64: rounding them through float32 would have moved 0.25% of the flop buckets and 0.13% of the turn buckets of these 2M deals. Preflop and river are unaffected.

### Projection to the 20M target

- Generation: about 85 min pinned to CPUs 8-15 (8 workers), or about 45 min on all 16 CPUs of an idle PC.
- Disk: 2.6 GB.
- `load_deals`: about 0.6 s warm, 340 MB of arrays.
- Re-bucketing: 20-50 s.

## Task 20: the blueprint in the bot (v3) and the v3 gate

v3 = `PolicyBot()` with `data/blueprint.npz` loaded: the CFR blueprint is the base layer,
the exploit layer runs on top, and the heuristic (v2's base) answers whenever the blueprint
cannot. v2 = `PolicyBot(use_blueprint=False)`, decision for decision.

### The layer chain (`bot/policy.py`)

- **Warmup** builds the betting tree, loads the bucket tables and the blueprint
  (`Blueprint.load`: format, rules, tree hash, bucket-table hash, shape), and self-tests
  it on the warmup hand (every street, facing a bet): every spot must map to a node and
  get a legal action. A missing file means no blueprint; a corrupt or stale file, or a
  failed self-test, is a failed warmup step and the bot plays v2. Warmup never raises.
- **Per decision**: `node_of(obs)` -> the bucket for (street, hole, board), cached in
  memory per (street, hole, board) -> `Blueprint.act(node, bucket, legal, rng, purify)`.
- **Fallback to the heuristic** on a node miss (counted in `memory["layers"]`, not a
  fault), `config_ok` False (the half's stack, blinds and raise cap vs the blueprint's
  meta), no blueprint, or any exception or illegal answer (a `blueprint` fault).
- **Exploits on a blueprint base**: check-folder and I6 need no Features and apply as in
  v2. The maniac and station re-runs need Features: they are computed only while such a
  mode is active, so the common decision stays cheap. In those modes v3 plays v2's
  validated exploit, never tighter than the blueprint (the re-run's no-extra-fold guard
  keeps the blueprint's action).
- **CPU sample (T11 M2)**: every preflop decision runs the preflop heuristic layer as the
  online CPU-factor sample, whichever layer answers. It draws no random numbers there.
- **Tuning knobs** (constructor, picklable): `purify` (default 0.1), `blueprint_streets`
  (default all), `exploit_features` (default True).

### Tests

`tests/test_policy_blueprint.py` (25 tests, default suite, about 3 s): the plan's
`test_blueprint_layer_used_when_config_ok`; the positive blueprint path skips the
heuristic (T11 M3: postflop it never runs, preflop only as the CPU sample); config
mismatch (raise cap, blinds, stack) and blueprint-meta mismatch never consult it; node
miss, a raising/illegal/non-Action blueprint and a failing bucket fall back to the
heuristic (the last three as `blueprint` faults); the bucket is computed once per street
and never reused for another hole; `blueprint_streets`; check-folder on a blueprint base;
re-run modes get Features only while active; a real `Blueprint` object (synthetic
max-action table at the runtime's 400 buckets) drives the bot; a missing, corrupt or
stale file means v2; warmup drops a blueprint that fails its self-test and keeps a
working one; the factories pickle. The heuristic-layer tests in `tests/test_policy.py`
and `tests/test_exploit.py` (and the tuner) pin `use_blueprint=False`, so the suite
holds with or without `data/blueprint.npz` (both states run green). The slow
`test_zero_errors_vs_whole_zoo` now also asserts that the blueprint answered when the
file is present.

### Running the gate (`sim/gate_v3.py`)

After the final export, on free CPUs (R39: CPUs 0-7 pinned, 2 workers, nothing else on
0-7). LBR has no clock, so it may run on the other cores at the same time:

```
.venv/bin/python -m sim.gate_v3 --out train_data/gate_v3 --cpus 0-7 --workers 2 --sections abce
.venv/bin/python -m sim.gate_v3 --out train_data/gate_v3 --cpus 8-15 --lbr-workers 8 --sections d
.venv/bin/python -m sim.gate_v3 --out train_data/gate_v3 --summary-only
```

Defaults: (a) 5 seeds x 1000 deals; (b) HOLDOUT + FIELD, 3 seeds x 1000 deals, scales
1.0 and 2.5, with the opponents' max bank per half; (c) from every match of a and b;
(d) LBR at 2000 particles, 16 seeds x 250 deals, ModelCheckError reported (exit 2);
(e) purify {0, 0.05, 0.1, 0.2} vs v2 on TRAIN, 2 seeds x 1000 deals
(`--extra v3_post v3_nofeat` adds the tuning variants). Every job is cached as JSON
under `--out`: rerun the same command to resume. One `--out` holds one blueprint's
results (another blueprint is refused, exit 3). The summary also goes to
`<out>/summary.txt`.

## v3.2: strict maniac mode on the blueprint base (2026-11-08 audit)

Finding: the maniac exploit mode (`bot/exploit.py`, detector `is_maniac()` at raise rate > 0.55) overrode the blueprint's action against strong aggressive bots: 76% of decisions in mode vs Posterior (28% changed), 47% vs SharkTank (19% changed). Removing the override entirely gained +2.78 / +1.47 bb/deal against them but lost the station fallback against station-flagged maniacs (−4.3 vs the maniac archetype).

Fix: `active_mode(opp, strict_maniac)` with `STRICT_MANIAC_MIN_RATE = 0.75`; `PolicyBot(strict_maniac=True)` applies it on the blueprint base only (`strict_maniac=False` reproduces v3.1 exactly). Below the rate the check falls through to "station".
